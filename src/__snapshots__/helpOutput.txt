=== assist sync --help
Usage: assist sync [options]

Install commands as ~/.agent/skills/<name>/SKILL.md, so they take precedence over a project skill of
the same name, and delete any ~/.agent/commands/<name>.md an earlier sync copied; when codex is
detected, also install commands as ~/.codex/skills/<name>/SKILL.md and register the assist
codex-hook in ~/.codex/config.toml, which auto-approves read-only commands and injects the repo's
composed advice on SessionStart; when pi is detected, also install commands as
~/.pi/agent/prompts/<name>.md and install the assist extensions into ~/.pi/agent/extensions, which
gate permissions and inject the same advice. No global instructions file is written — every harness
composes its own from assist advise at session start, and any ~/.claude/CLAUDE.md,
~/.codex/AGENTS.md or ~/.pi/agent/AGENTS.md an earlier sync left behind is named so you can remove
it. A target that exists and was not written by sync is never overwritten or deleted without
confirmation; with --yes it is left in place and reported. With --prune, also report files an
earlier sync wrote that assist no longer ships, and with --prune --force remove them

Options:
  -y, --yes   Overwrite settings.json without prompting
  --prune     After syncing, list files an earlier sync wrote (recorded in
              ~/.assist/sync-manifest.json) whose name is no longer in the repo's
              agent/commands/*.md set; files sync did not write are listed separately and never
              removed
  --force     With --prune, remove the listed orphaned files; a claude or codex skill directory is
              removed only when SKILL.md is its sole content. Errors without --prune
  -h, --help  display help for command

Config:
  assist config set sync.autoConfirm true --node # skip the settings.json overwrite prompt
  assist config set sync.preferences true --node # also merge assist's author preferences (claude/preferences.json) into settings.json

=== assist run add --help
Usage: assist run add [options] <name> <command> [args...]

Add a new run configuration to assist.yml, or with --repo to the shared db

Arguments:
  name                     Name for the run configuration
  command                  Command to execute
  args                     Static args to pass to the command

Options:
  --cwd <dir>              Working directory (resolved relative to the config file)
  --server [group]         Mark as a singleton dev server, optionally in a named group (default
                           group: default)
  --port <port>            Display-only port shown on the serving card
  --protocol <http|https>  Protocol for the serving card's port link (default: http)
  --path <path>            Path for the serving card's port link, e.g. /swagger (default: /)
  --env <KEY=VALUE>        Environment variable for the command (repeatable)
  --pre <command>          Shell command run first (repeatable)
  --filter <glob>          Only run a verify: entry when a changed file matches
  --quiet                  Suppress output unless the command fails
  --param <spec>           Positional param: <name>, <name>! (required) or <name>=<default>
                           (repeatable)
  --repo [name]            Write to a repo's override in the shared db, seen by every node, instead
                           of assist.yml (defaults to the current repo; no command file is created)
  -h, --help               display help for command

Run entry properties:
  name      <name>                   what you type after assist run
  command   <command>                executable to spawn
  args      [args...]                static args appended to the command
  cwd       --cwd <dir>              working directory, relative to the config file
  env       --env KEY=VALUE          environment variable for the command (repeatable)
  server    --server [group]         singleton dev server, optionally grouped
  port      --port <port>            display-only port on the serving card
  protocol  --protocol <http|https>  protocol of the serving card's port link (default: http)
  path      --path <path>            path of the serving card's port link, e.g. /swagger (default: /)
  pre       --pre <command>          shell command run before this one (repeatable, runs in order)
  filter    --filter <glob>          verify: entries only run when a changed file matches this glob
  quiet     --quiet                  suppress the command's output unless it fails
  params    --param <spec>           positional param filled from assist run args (repeatable, see below)

The command is spawned without a shell, so "FOO=bar cmd", "&&", pipes and redirects do not work; use --env for environment variables and --pre for setup steps (--pre commands do run in a shell).

Options go after <command>. --server and --repo take the next argument as their value unless it starts with "-", so put them last or before another option:
  assist run add dev npm run dev --env PORT=3000 --server --port 3000 --repo
These flags are taken from anywhere after <command>; to pass one to the command itself, quote the whole command:
  assist run add build "pnpm --filter web build"

--param <spec> appends params in order; each fills the next arg given to assist run:
  <name>            optional, omitted when not given
  <name>!           required, assist run fails when it is missing
  <name>=<default>  used when not given
  assist run add deploy ./deploy.sh --param env! --param tag=latest   # assist run deploy prod → "./deploy.sh prod latest"
A param's description is set in config.

--what, and --why:

  --title <title>   short PR title.
  --what <what>     what the change does (rendered as ## What).
  --why <why>       why the change is needed (rendered as ## Why).
  --how <how>       optional; how the change works (rendered as ## How). Omit it

  --resolves <key>  Jira issue key resolved by this PR; repeatable. Each key's

Screenshots: pass --screenshot '[Group/]Caption=path' once per image or video
(png, jpg, jpeg, gif, webp, svg, mp4, webm, mov). gh 2.99.0+ uploads each
file and the body gets a ## Screenshots section: one ### Group heading per group
with its images in a 2-column captioned table (so light/dark pairs sit side by

  --screenshot 'Profile/Career Connect light=shots/profile-light.png'
  --screenshot 'Profile/Career Connect dark=shots/profile-dark.png'

Wrap symbols, file paths, function names, class names, variable names, config
keys, CLI commands, and flag names in backticks.

One section, one question. Each section answers exactly one thing, and
implementation detail lives only in ## How:

  ## What  what is observably different for someone using or calling this, and
           nothing else. Not how it's built, not which functions/files changed.
  ## Why   the problem or motivation that made the change worth doing. Not how
           the solution works.
  ## How   only the non-obvious decisions the diff alone won't explain: a
           deliberate trade-off, a workaround, a reason the obvious approach was
           rejected. Omit it entirely by default. Never restate ## What as
           mechanism, and never walk through the diff.

The most common failure is altitude bleed: an implementation detail gets sprayed
into whichever section is being written — ## What narrates the diff, ## How
restates ## What, ## Why smuggles in mechanism. If a sentence describes a
mechanism, it belongs in ## How, and probably shouldn't exist at all unless it's
a genuine non-obvious decision. Litmus — a sentence is almost certainly mechanism
(so ## How, or cut it) if it contains "by …ing", "so that it can", "because the
X filters/needs/uses", or names an internal component, property, function, or
file.

Brevity budget — one paragraph per section, and these are ceilings, not targets:

  ## What  2–3 sentences.
  ## Why   1–2 sentences.
  ## How   omit by default; a sentence or two, only for non-obvious decisions.

The budget is a total, not a per-paragraph allowance. Splitting a section across
two paragraphs buys no extra room. The whole body should read in well under a
minute — roughly 6 sentences and 900 characters of prose for a typical change,
counting every section together. A body that is long-winded overall is wrong even
when each paragraph is individually short.

Terse technical register. Write like a commit message, not a report. Short
declarative sentences, one clause each: state the fact and stop. Cut
scene-setting, restatements of the heading, "this change …", "in order to", "it
is worth noting", hedges ("essentially", "fairly", "somewhat"), and adverbs that
carry no information. Present tense, active voice. If a sentence can lose half
its words and still say the same thing, it is too long.

  Wordy: This change introduces a new validation step so that the command is
         able to reject pull request bodies which exceed the configured limit.
  Terse: Rejects bodies over the limit.

Sentence count is a floor on brevity, not the whole of it — a body inside the
budget can still be too verbose, and then it needs cutting rather than reflowing.
Prefer deleting a sentence to shortening it.

Write prose. A short paragraph is the natural form for ## What and ## Why —
bullets in ## What are a smell. Use bullets only when there are genuinely several
independent, parallel items (3+); a single bullet is never right. A single
non-list paragraph over ~600 characters or ~4 sentences is a wall of text and
will be rejected.

only individual sections (every other section of the existing body is preserved).

Update individual sections of the current branch's pull request. Only the sections
you pass are replaced; every other section of the existing body is preserved.

Do not reference Claude or any AI assistance in the title or body. Wrap symbols,
file paths, function names, class names, variable names, config keys, CLI
commands, and flag names in backticks.

A replacement section is held to the same standard as one written by
'assist prs raise', and the budget applies to the resulting body as a whole — an
edit must not push the body over it. Read the sections you are not touching first:
if the section you are replacing was the concise one, trimming it further will not
rescue a body that is already long-winded.

  ## What  what is observably different for someone using or calling this.
  ## Why   the problem or motivation that made the change worth doing.
  ## How   only non-obvious decisions the diff alone won't explain; omit by
           default.

Screenshots: pass --screenshot '[Group/]Caption=path' once per image or video
(png, jpg, jpeg, gif, webp, svg, mp4, webm, mov). gh 2.99.0+ uploads each
file and the body gets a ## Screenshots section: one ### Group heading per group
with its images in a 2-column captioned table (so light/dark pairs sit side by
side), then any ungrouped images as plain images. The spec splits on the first '=' (label vs
path), then the label on the first '/' (group vs caption); a missing caption
falls back to the file name. A missing file or unsupported extension fails the
command before anything is previewed or sent. Never author ## Screenshots in a
section option yourself.

  --screenshot 'Profile/Career Connect light=shots/profile-light.png'
  --screenshot 'Profile/Career Connect dark=shots/profile-dark.png' On edit, any supplied screenshots replace the existing
## Screenshots section rather than adding a second one, so pass the full set.

Brevity budget — one paragraph per section, and these are ceilings, not targets:

  ## What  2–3 sentences.
  ## Why   1–2 sentences.
  ## How   omit by default; a sentence or two, only for non-obvious decisions.

The budget is a total, not a per-paragraph allowance. Splitting a section across
two paragraphs buys no extra room. The whole body should read in well under a
minute — roughly 6 sentences and 900 characters of prose for a typical change,
counting every section together. A body that is long-winded overall is wrong even
when each paragraph is individually short.

Terse technical register. Write like a commit message, not a report. Short
declarative sentences, one clause each: state the fact and stop. Cut
scene-setting, restatements of the heading, "this change …", "in order to", "it
is worth noting", hedges ("essentially", "fairly", "somewhat"), and adverbs that
carry no information. Present tense, active voice. If a sentence can lose half
its words and still say the same thing, it is too long.

  Wordy: This change introduces a new validation step so that the command is
         able to reject pull request bodies which exceed the configured limit.
  Terse: Rejects bodies over the limit.

Sentence count is a floor on brevity, not the whole of it — a body inside the
budget can still be too verbose, and then it needs cutting rather than reflowing.
Prefer deleting a sentence to shortening it.

Write prose. A short paragraph is the natural form for ## What and ## Why —
bullets in ## What are a smell. Use bullets only when there are genuinely several
independent, parallel items (3+); a single bullet is never right. A single
non-list paragraph over ~600 characters or ~4 sentences is a wall of text and
will be rejected.

=== assist review --help
Usage: assist review [options] [number]

findings, or check out a PR by number first when given; --checkout-only just checks the PR out and
leaves an idle session in the checkout tree

Arguments:
  number                Optional PR number; when provided, runs `gh pr checkout <number>` before
                        reviewing

Options:
  --harness <kind>      Coding harness (claude|codex|pi) for the interactive session that --refine,
                        --apply, --backlog, --checkout-only or --high-level starts, and for the
                        Address Comments session --address-comments chains; defaults to the
                        configured harness.engine. Exits with the reasons, before checking out or
                        reviewing, when that session is unavailable on it. Reviewers and synthesis
                        are not affected (see review.synthesisHarness)

  --force               Clear cached claude.md / codex.md / synthesis.md and re-run all phases; with

                        starting/done lines)

Usage: assist slack post [options] [channel]

Preview a markdown message, or a thread of them with --parts, bound for a Slack channel (body of -
reads it from stdin)

Options:
  --body <body>               Message body (- reads it from stdin)
  --parts <files...>          Files holding the messages of one thread, in thread order (not with
                              --body)
  --thread <ts-or-permalink>  Reply in this thread: a message ts (1712345678.123456) or a Slack
                              archives permalink
  -h, --help                  display help for command

The command does not post: Slack is reachable only over MCP, so it previews the message and hands the approved body back for /slack-post to send.
In an assist web session the body is previewed for approve/reject first (with inline comments). On approval the body is written to a working file under ~/.assist/slack/ and its path printed on the last line, preceded by the resolved thread_ts when --thread was given. On rejection nothing is handed back: the command exits non-zero with the reason and any inline comments, leaving the previewed markdown in the working file to revise in place.
--parts takes the files holding one thread's messages in thread order, each getting its own working file (channel-1.md, channel-2.md, …) and its own preview pane titled with its position in the batch (2/3). The panes pop in sequence and no path is printed until every part is approved, at which point each path prints prefixed with its position (1/3) under a line naming the target, followed by how to thread them: without --thread part 1 opens the thread and the rest carry the thread_ts it returns, with --thread every part is a reply under the resolved thread_ts. The first rejection halts the batch and exits non-zero naming that part's position, reason, inline comments and working file, with no path handed back. A missing or empty part file, or --parts with --body, is an error before any pane opens.
Outside a web session there is no preview and the body passes straight through.
slack_send_message accepts standard markdown as it is — bold, italic, code, blockquotes, lists, links, code blocks, tables and headers — capped at 5000 characters.
